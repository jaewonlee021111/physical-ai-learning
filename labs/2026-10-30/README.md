## 핵심

프로젝트는 결과·범위·책임·완료 조건에 대한 약속이다. 요구, 설계, 작업, 시험, 인계가 서로 연결돼야 한다. 오늘 교안은 개인 기획·자기 점검이며 실제 팀 편성이나 팀 승인 완료를 가정하지 않는다.

| 개념 | 정리 |
| --- | --- |
| RACI | 수행 R, 최종 책임 A, 협의 C, 공유 I를 정함 |
| 수용 기준 | 개별 요구가 충족됐는지 확인하는 조건 |
| 완료 기준 | 코드·시험·문서·검토 등 공통으로 갖춰야 할 조건 |
| 위험·이슈·결함 | 앞으로 생길 불확실성·이미 생긴 문제·기대와 실제의 불일치 |
| 추적성 | 요구 ID를 설계·작업·시험·결과와 연결 |
| 검증·타당성 확인 | 명세대로 만들었는가·사용 목적에 맞는가를 구별 |
| 인수인계 | 실행·환경·원본 버전·막힘·복구·다음 작업 전달 |

## 표준을 적용하는 관점

프로젝트 관리, 시스템/소프트웨어 생애주기, 요구공학, 아키텍처 설명, 문서, 품질 모델, 시험 프로세스·문서, 사람 중심 설계·접근성, 조직 관리체계의 범위를 구별한다. 수업에서는 관련 관점을 요구와 확인 방법으로 옮긴다. 표준 원문 전체 검토나 제품·조직 인증 완료를 뜻하지 않는다.

## 적용 산출물

[라즈봇 주제에 적용한 개인 기획 초안](PROJECT-PLAN.md)을 작성했다. 기존에 합의한 목표를 기반으로 요구·모듈·작업·시험을 연결한 학습용 초안이며 팀의 공식 승인·담당자 배정·하드웨어 검증을 대신하지 않는다.

공식 교안은 22개 양식과 작성 예를 제공하지만 처음부터 전부 작성·제출하라는 뜻은 아니다. 프로젝트 크기에 맞게 묶고 가장 불확실한 기능을 먼저 시험한다.

## 다음 개발에 넘길 것

- 인식 결과와 거리값의 데이터 계약부터 합의한다.
- GOAL 접근·정지 최소 기능을 구현하고 실물에서 시험한다.
- 실행 버전·환경·입력·기대·관찰·증거를 남긴 뒤 회전과 손동작으로 확장한다.
- 시험 결과가 없는 항목은 NOT_RUN을 유지한다.
