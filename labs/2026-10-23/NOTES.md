# 개념과 문제 해결

## 통신 방식

- **STA**: 보드가 공유기에 접속한다. PC·보드의 네트워크 경로가 있어야 로컬 IP로 접속할 수 있다.
- **SoftAP**: 보드가 Wi-Fi 네트워크를 만든다. 인터넷 공유 기능을 구현한 것은 아니다.
- **BLE**: GAP은 광고·검색·연결, GATT는 서비스·특성 읽기·쓰기·알림의 구조를 다룬다. 사용자 정의 UUID를 표준 프로파일로 혼동하지 않는다.
- **클라우드 제어**: 브라우저가 원하는 LED 상태를 쓰고 보드가 HTTPS로 주기적으로 읽는다. 터치 상태는 보드가 보고한다. 이 실습은 폴링이며 WebSocket 실시간 구독 구현과 다르다.
- **Tailscale**: PC 게이트웨이와 휴대폰을 연결한다. ESP32 자체에 Tailscale을 설치하는 구조가 아니다.

## 정확히 구분하기

ESP32-S3의 Wi-Fi는 2.4 GHz다. RSSI는 일반적으로 0에 가까울수록 강하지만, -70 dBm 같은 수치 하나로 연결 가능 여부를 확정할 수 없다. MAC 주소는 임의화·위조될 수 있어 인증 수단이 아니다. PSRAM은 추가 RAM이며 GPU 전용 VRAM과 다르다. BLE와 Bluetooth Classic은 용도·지원 기능이 달라 항상 어느 쪽이 더 우수하다고 할 수 없다.

## 확인 순서

1. 컴파일 실패와 업로드 실패를 구분한다. COM4는 수업 예시이며 본인 포트를 사용한다.
2. 업로드가 안 되면 다른 모니터의 포트 점유, USB 데이터 케이블, BOOT/RESET 상태를 확인한다.
3. LED는 XIAO 내장 LED의 active-low 논리를 사용한다. 외장 LED 회로와 핀을 섞지 않는다.
4. 터치 값이 불안정하면 전원 인가 직후 만지지 않고 다시 보정하고 도선·주변 환경을 확인한다.
5. 웹 접속이 안 되면 IP·같은 LAN·2.4 GHz·공유기 격리를 확인한다. AP 모드에서는 휴대폰이 보드 Wi-Fi에 연결됐는지 확인한다.
6. 카메라는 `/capture`, `/status`, `/stream` 순으로 확인한다. 정지 사진만 된다고 스트리밍 성공으로 기록하지 않는다. PSRAM·배선·핀·카메라 초기화 로그를 확인한다.
7. PC 영상은 먼저 `--no-yolo`로 전송을 확인한 뒤 모델을 켠다. CPU 부하와 무선 품질 문제를 나눠 확인한다.
8. BLE는 광고 검색 → 연결 → 서비스 확인 → ASCII 쓰기 → 알림 구독 순서로 확인한다. 브라우저 지원 여부를 먼저 확인한다.

코드 생성 프롬프트에서 요구한 핀·서버 포트·PSRAM·타임아웃·버퍼 반환·주석 규칙은 구현에 반영했다. 버전은 PlatformIO 설정으로 고정하고 카메라 라이브러리를 중복 설치하지 않는다.
